The new flagged page_access_claim reuses real M2 allocation, M3 mapping checks
and exact-owner rollback without calling any injected backend. Both numeric
outputs must be disjoint from authority metadata before allocation. A claim
is uninitialized and must remain private within its outer exclusion until a
fixed direct initialization leaf and release/publication complete.

The memory-boot diagnostic authenticates through the same D5.7 adapter before
reading metadata. It deliberately rejects an unsupported map width and proves
rollback/output preservation, then claims actual boot RAM. Direct calls to the
existing kernel_page_zero leaf and full-page readback prove zeroing, a 0xa5
write, invalid-length rejection without a write, and successful zero again.
Wrong-owner release is refused; exact-owner release restores accounting.
No arbitrary backend is invoked in that guarded transaction; no page pointer
escapes. Unexpected failure retains IF=0 and uncertain storage for diagnosis.
Both independently stacked workers run it inside their existing transaction.

This is the page gate ONLY. General legacy caller admission, runtime binding,
root reset/retirement lifetime and executing/referenced-stack protection remain
unfinished. MEMORY_WIRING_TEST has not been implemented by this page child.
The generic callback-based M3 API and default kernel behavior stay unchanged;
that legacy API is not certified for preemptible task callers.
