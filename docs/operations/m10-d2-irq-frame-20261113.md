## Why this work is separate from preemption

M10-B cooperative switches save only SysV callee-saved registers. M10-D
true timer preemption must preserve **every** live GPR and the CPU's
interrupt-return frame; reusing the M10-B switch from inside an ISR would
lose volatile registers or transfer to an invalid stack. D2 proves
preservation but deliberately does not hand ownership to another task,
alter the IRQ vector, change LAPIC EOI count or modify the running editor.

## Hardware frame contract

The M9 IRQ0 entry pushes RAX, RBX, RCX, RDX, RSI, RDI, RBP, R8,
R9, R10, R11, R12, R13, R14, R15. Because the stack grows downwards,
the frame pointer after pushes addresses the following uint64 slots:

| Slot | Interrupted state |
|---|---|
| 0..14 | R15,R14,R13,R12,R11,R10,R9,R8,RBP,RDI,RSI,RDX,RCX,RBX,RAX |
| 15 | RIP |
| 16 | CS |
| 17 | RFLAGS |
| 18 | original RSP |
| 19 | original SS |

For an external x86-64 vector without CPU error code, in **64-bit
mode** the processor unconditionally pushes SS:RSP even for
same-privilege ring-0 interrupt delivery. It may independently
realign the handler stack; original RSP is taken from slot 18, not
guessed from the current ISR RSP plus a constant. The test only runs
on QEMU boot CPU, ring 0, IST=0. A different CPL/IST policy requires
separate review before actual handoff.

Authoritative reference: Intel Software Developer's Manual, Volume 3A,
section 7.14.2 (64-Bit Mode Stack Frame):
https://cdrdv2-public.intel.com/874240/325462-090-sdm-vol-1-2abcd-3abcd-4.pdf

## Test-only code and ownership

- `src/kernel/m10-d2-irq-frame.[ch]` defines named slot indices,
  checks 15 distinct 64-bit sentinels, RIP within one assembly spin
  loop, same CS and SS, actual saved RSP and IF/mandatory FLAGS bits.
- `src/kernel/m10-d2-probe-run.S` preserves six callee-saved
  registers at entry, writes the sentinel values into all 15 registers
  and spins without yielding until three real IRQ0 observations. It
  then independently checks its six callee-saved registers after IRETQ
  and returns to the unchanged boot path.
- `src/kernel/x86-irq0.S` calls the checker **only** with the special
  `SPIFFOS_M10_D2_IRQ_FRAME_TEST` build flag, after the ordinary C
  tick handler performs the unchanged LAPIC EOI. The checker does no
  allocation, I/O, locks, stack changes or scheduling.
- `src/kernel/main.c` runs the probe after boot-ready diagnostics
  and before starting normal keyboard polling, only for the diagnostic
  build. On mismatch it serializes `SPIFFOS_M10_D2_FRAME_ERROR`
  outside IRQ context and halts.
- `scripts/test-m10-d2-guest.py` builds in a private temporary
  source tree and boots QEMU with private OVMF variables at
  128/256/512 MiB, then builds a **second deliberately incorrect
  expected-R15** diagnostic and demands a fail-closed FRAME_ERROR.
  No production image is modified. Source Makefile allows a
  `make HOST_CC=gcc test-m10-d2-guest` or the full
  `make HOST_CC=gcc test-m10-d2-acceptance` regression gate.

## What this does not prove

No actual task handoff, non-trivial task-stack lifetime or
ownership transfer occurs in D2. No guarantees for live FP/SIMD,
SMP, ring-3 privilege transition, different IST, task CR3 or
nested IRQ entry. D3 must test a separately reviewed IRQ-exit
handoff with two CPU-bound non-yielding tasks, then D4 must test
actual starvation and supervisor CPU service under load.
